# Affiliate Captain – Operator handbook

This handbook is for the people who run a partner program with Affiliate Captain: shop owners, administrators and the person who does the payouts. Developers integrating other sales sources find the public contract in [CONTRACT.md](CONTRACT.md) and the REST API in [REST.md](REST.md).

> Legal note: cookie consent, VAT treatment of credit notes and retention periods depend on your country and business. The plugin gives you the tools; have the setup reviewed by your data protection and tax advisors.

## 1. Requirements and setup

**Requirements:** WordPress 6.3 or newer, PHP 8.5 or newer with the extensions `sodium` (encryption of bank details) and `dom` (SEPA XML), optionally `zip` (program export). MySQL 9.7 (LTS) or newer, or MariaDB 12.3 (LTS) or newer, with InnoDB tables (bookings run in transactions). An older database server does not block activation or bookings, but it is no longer tested: Site Health (Tools → Site Health, test "Partner program") shows the warning "The database server is older than the supported minimum" with the detected version until the server is updated. The minimums are the constants `MYSQL` and `MARIADB` of `WPAffiliateCaptain\Core\Requirements`; the filter `wpac_minimum_db_versions` (array with the keys `mysql` and `mariadb`, since 0.15.0) changes them, e.g. on a host whose older server you have tested yourself. WooCommerce is optional (8.0 or newer; the partner code field in the block checkout needs 8.9 – with 8.0 to 8.8 only the classic checkout shows it, and Settings → Tracking says so).

**Database replicas and clusters.** The plugin protects parallel bookings of the same order (a refund webhook arriving while the sale is being booked, two cron runs) with MySQL user locks (`GET_LOCK`, `IS_USED_LOCK`, `RELEASE_LOCK`). These locks live on the server of the connection:
- With a read/write split (HyperDB, LudicrousDB, ProxySQL with read replicas) all queries of the plugin tables must go to the primary – at least the lock functions and the reads right after them. Configure the plugin's tables (`{prefix}wpac_*`) and the lock functions as "write" in the splitter; otherwise a lock taken on the primary is invisible to a check that runs on a replica.
- Galera/Percona XtraDB Cluster: user locks are local to the node and not replicated, and `pxc_strict_mode=ENFORCING` may refuse them. Send all writes of the site to one node (the usual single-writer setup); with several writers parallel requests for the same order are not serialised.
- The migration lock is an option row (not a user lock) and works everywhere.

**Before you activate** – add to `wp-config.php`:

```php
// Own key for the encryption of partner bank details: 64 hex characters,
// e.g. from: php -r 'echo bin2hex(random_bytes(32));'
define( 'WPAC_ENCRYPTION_KEY', '…' );

// Credit notes outside the web root (required on nginx, where .htaccess has no effect).
define( 'WPAC_STATEMENT_DIR', '/var/www/private/wpac-statements' );

// Optional (lifetime commissions): own key for the customer hashes, at least 32 characters.
define( 'WPAC_CUSTOMER_KEY', '…' );
```

**Several app servers** (load balancer): use object storage (next section) – or the statement folder must be shared storage mounted at the same path on every server (NFS, EFS …), set with `WPAC_STATEMENT_DIR` or the filter `wpac_statement_dir`. Without it a download on another server finds no file – the plugin then builds the document again from the stored data (identical when nothing relevant changed, otherwise marked as *duplicate*). The deletion after the retention period is decided in the database: the daily cron deletes the files on its own server and marks the documents as deleted; the plugin's hourly cron sweeps the folder of the server it runs on at most every 6 hours (filter `wpac_statement_sweep_interval`, seconds; 0 = only by command; `wpac_statement_sweep_budget` limits the seconds per run including the folder listing, default 20), and a copy is deleted whenever a deleted document is requested on that server (it is never served or rebuilt again). Visitor requests never sweep (the filter `wpac_statement_sweep_on_requests` can turn that on again, default off). Because WP-Cron runs on whichever server serves the triggering request, run `wp wpac statements sweep` (add `--network` on a multisite) on **every** app server from its system cron, e.g. daily. Only files whose SHA-256 belongs to a deleted credit note, cancellation or correction credit note are removed; other files in the folder are listed and kept. Each server keeps the time of its last sweep in the file `.wpac-sweep` in its statement folder; it holds only hashes of the files remembered as unknown, never file names or paths.

### Credit notes on several servers: S3-compatible object storage

Instead of a folder, the credit notes, correction credit notes and cancellation documents (PDF) can be kept in S3-compatible object storage (AWS S3, Hetzner Object Storage, Wasabi, MinIO, Cloudflare R2 …). Every app server then reads and deletes the same, only copy: downloads work on every node, and the deletion after the retention period reaches every node at once – the per-node sweep (`StatementSweep`, `wp wpac statements sweep`) is not needed and its automatic run is skipped. Requests are signed with AWS Signature Version 4 and sent through the WordPress HTTP API (no SDK). The e-invoice XML is not stored (it is built from the stored data on each download), so nothing else goes to the bucket.

Configuration only in `wp-config.php` (never stored in the database or shown in the admin; placeholder values):

```php
define( 'WPAC_S3_ENDPOINT', 'https://fsn1.your-objectstorage.com' ); // required, also for AWS (e.g. https://s3.eu-central-1.amazonaws.com)
define( 'WPAC_S3_REGION', 'fsn1' );                  // e.g. eu-central-1; Cloudflare R2: auto
define( 'WPAC_S3_BUCKET', 'example-credit-notes' );
define( 'WPAC_S3_KEY', 'EXAMPLEACCESSKEYID' );
define( 'WPAC_S3_SECRET', 'example-secret-access-key' );
define( 'WPAC_S3_PREFIX', 'affiliate-captain/' );    // optional; a network adds site-<id>/ per site
define( 'WPAC_S3_PATH_STYLE', true );                // optional: https://endpoint/bucket/key (MinIO, some providers)
define( 'WPAC_S3_SSE', 'AES256' );                   // optional: server-side encryption header (AES256 or aws:kms)
```

- The bucket must be **private** (no public access, no public listing); objects are written without any ACL. Give the key only the rights for this bucket (or prefix): `PutObject`, `GetObject`, `DeleteObject`, `ListBucket`. The endpoint must use HTTPS (plain HTTP only for a local MinIO on `localhost`).
- Incomplete constants (e.g. the secret missing): the plugin keeps using the local folder and Site Health reports it as critical, naming the missing constants (never their values).
- **Affiliate Captain → Integrations → System status → Document storage** shows the active store (bucket, prefix, host, region – no key or secret), the last failure and a **Test connection** button (writes, reads and deletes a probe object). Also `wp wpac statements test`.
- Existing documents: `wp wpac statements migrate --to=s3 --dry-run` lists the documents in the local folders of this server, `wp wpac statements migrate --to=s3` uploads them, reads each one back and compares its SHA-256 before the local file is deleted (failed copies stay local). Run it on every app server that kept its own folder. Until then the documents are still read from the local folder; the Integrations page and Site Health count them.
- Failures: a credit note that cannot be stored keeps its number and hash; it is written again by the hourly job with growing pauses (1, 2, 4 … 24 hours), logged, and Site Health shows the error. A document that cannot be deleted after the retention period is not marked as deleted and is tried again the next day.
- Uninstall ("delete all data") deletes this site's documents in the bucket as well; deleted sites of a network: their `site-<id>/` prefix is emptied when their period ends.
- A custom store (another storage system) can be supplied with the filter `wpac_statement_store` (an object implementing `WPAffiliateCaptain\Payouts\Storage\StatementStore`); it must be the same on every server. The default without any configuration is the local folder, unchanged.
- **Privacy:** the credit notes contain personal data of the partners (name, address, tax number / VAT ID, masked IBAN). The storage provider processes them on your behalf: conclude a data processing agreement (Art. 28 GDPR, Auftragsverarbeitung) and choose the data location of the bucket (region; inside the EU/EEA, or note the transfer to a third country with its safeguards in your records of processing and privacy policy). The retention deletion removes the objects; versioning or object lock on the bucket would keep copies – leave them off or align their deletion with the retention period.

Set both **before** the first partner enters bank details and the first credit note is written. Without `WPAC_ENCRYPTION_KEY` the key is derived from the WordPress salts – changing the salts later makes stored IBANs unreadable. Keep a copy of the key in your password manager: without it, bank details cannot be decrypted after a server move.

**Setup checklist.** After activation, Affiliate Captain → Dashboard shows a checklist. "Create pages automatically" adds the application form, the partner area and a landing page with the matching blocks. Then go through Settings:

| Tab | What to set |
|---|---|
| Program | application and partner area pages, terms page and version, automatic approval, open commissions on termination |
| E-mails & reports | notification e-mail, e-mail sender, optional partner e-mails, monthly summary mails |
| Tracking | link parameter (default `partner`), checkout field, shop session, cookie mode, attribution (first/last touch), JavaScript tracking for caches |
| Fraud & abuse | fraud rules, rate limit, trusted proxies (Cloudflare/reverse proxy IP ranges) |
| Commissions | program currency (changing it converts the minimum payout, review limit and a fixed default rate – with an exchange rate between the two currencies if one is entered; fixed rules and bonus tiers must be adjusted by hand), exchange rates for reports, default rate, rule precedence, lifetime commissions, subscription renewals, hold period |
| Promotion | landing page path, disclosure note, visible disclosure label in the banner embed code, promotion guidelines |
| Payouts & credit notes | minimum payout, payout requests, other payment method (on/off); your country, address, VAT ID/tax number; self-billing, VAT rate, number prefixes; VIES check; company bank account for SEPA |
| Data & maintenance | all retention periods (visits, rejected applications, audit log, statements, legal hold), maintenance mode, monitoring token, data deletion on uninstall, record of processing activities |

**Server cron.** Commissions are released, retries run and old data is deleted by scheduled tasks (hourly and daily). On sites with few visits or with `DISABLE_WP_CRON`, set up a system cron:

```
*/5 * * * * cd /path/to/wordpress && wp cron event run --due-now --quiet
```

On a multisite network `wp cron event run` only reaches the main site. Run it for every site:

```
*/5 * * * * cd /path/to/wordpress && wp site list --field=url | xargs -I{} wp cron event run --due-now --quiet --url={}
```

(or `wp wpac cron hourly --network` hourly and `wp wpac cron daily --network` daily). Without the loop, the other sites of the network neither release commissions nor finish a database update after a plugin update – the admin notice and Site Health show the command with the loop on a network.

**Copies of the site.** When the site address changes (staging copy, clone, backup restored on another domain), maintenance mode is switched on automatically and a notice explains it: the copy sends no report mails, alarms, VIES requests or payouts to real partners. After a real move of the site, switch maintenance mode off under Settings → Data & maintenance. The filter `wpac_clone_protection` (return `false`) turns the detection off.

**Updating by FTP/rsync.** Since 0.10 the main file is `affiliate-captain.php` (folder `affiliate-captain`). If you copy a new version over an old folder `wp-affiliate-captain/`, the old main file `wp-affiliate-captain.php` may stay active: the plugin then switches the activation to the new main file in the same folder by itself (from the next request on; the schema version is part of the code, so nothing runs with old version numbers meanwhile). An old copy in another folder is taken over the same way; "Delete all data on uninstall" is then switched off, so deleting the old copy cannot remove the shared data. A deployment that deletes the old main file (e.g. git) deactivates the plugin – activate "Affiliate Captain" again; nothing is lost.

## 2. Partners

**Applications.** The application form (block "Partner application form" or `[wpac_affiliate_registration]`) asks for name, e-mail, website and channel, plus the fields of the chosen partner group. Applicants confirm their e-mail address (double opt-in) and accept the terms; the version, time and accepted text are stored. Applications appear under Partners with the status "Application pending" unless automatic approval is on.

**Approval.** On approval the partner gets a WordPress account (or is linked to the existing one after confirming a link sent by e-mail – accounts with editing rights are never linked automatically) and a random partner code. Pause, termination and rejection need a reason, which is shown to the partner.

**Recruited by (since 0.15.0).** When someone applies on the registration page through another partner's referral – a partner code or vanity slug in the referral parameter of the registration URL (`/become-a-partner/?partner=CODE`), or, without it, a referral captured earlier for this visitor (session or consented cookie, as for orders) – the recruiting partner is stored with the new partner (database column `referred_by`, schema 16). Only active partners whose processing is not restricted count, never the applicant (same WordPress user, the same e-mail address as the partner or as the partner's WordPress account, compared as for self-referrals; since 0.16.0 also not when the application comes from the device of a current login of the recruiter's WordPress account – same address and browser, read from the WordPress login sessions for this comparison only, never for addresses of private networks or trusted proxies); the recruiter is checked again when the e-mail address is confirmed. Fraud plugins can add their own signals with the filter `wpac_is_self_recruitment`. The partner page (Profile → "Recruited by") shows and changes it (permission "Manage partners", audit entry `affiliate.referred_by`); a partner cannot be their own recruiter, and a cycle (A recruited B, B recruited A – also over several levels) is refused. The free plugin pays nothing for a recruitment: the link and the event `wpac_affiliate_recruited` (fired once when the recruited partner becomes active – automatic approval or approval of the application) are for add-ons such as sub-affiliate programs. The privacy export lists the recruiter's partner ID; an erasure keeps the ID as a pseudonymous link and deletes everything else as before.

**Partner groups** (Rules & groups) have their own terms page and version, their own application fields and their own commission rules – for example "Influencer" and "Schools".

**Several partner programs (since plugin 0.15.0, contract 1.5.0).** The free plugin runs one program. An add-on can turn partner groups into separate programs ("a program is a partner group", every partner in exactly one program) with their own default commission rate, hold period, cookie lifetime, attribution model, minimum payout and terms page. Without such an add-on nothing changes: all partners use the values of the settings. The program of a new partner is the group of the application form – put one application form per program on its own page (block "Partner application form" or `[wpac_affiliate_registration group="3"]`, or the form groups of the block). Moving a partner to another group (partner page → Profile) moves them to that program; deleting a group moves its partners to the default program. Commissions already booked keep their amounts and hold dates; in program filters and reports they count for the partner's current program. With such an add-on the dashboard shows a "Program" selector for the reports and the CSV export (the "Active partners" figure then counts the partners of the chosen program), the REST report route accepts `program`, and the partner's conditions can name the program. Since 0.16.0: the monthly bonus still closes a month after the hold period of the settings, but a partner whose program has a longer hold period gets the bonus only after that period (booked by the daily recalculation); the partner page shows the partner's own minimum payout when it differs, and the payout run names differing program minimums; the suggested privacy text names the range of cookie lifetimes (e.g. "between 30 and 90 days") when a program uses another lifetime – review it with your data protection advisor. Developers: [CONTRACT.md](CONTRACT.md), "Partnerprogramme (seit Vertrag 1.5.0)".

**Partner codes.** Every partner has at least one code (random by default, a custom code is possible). Codes can have a usage limit and an expiry date, be linked to a WooCommerce coupon, or be created in batches (with CSV export) for print campaigns. A linked coupon must exist in WooCommerce and must not be linked to another partner. A coupon that is not linked counts for a partner only when its code equals a generated partner code (random form such as K7Q3-MX2P, since 0.16.0): only a generated partner code works as a coupon by name, nobody names a shop coupon like that by chance. A code chosen by a person – a custom code or an approved code request such as MARIA10 – credits orders with a coupon only when the coupon is linked to the partner (field "Affiliate partner" on the coupon screen, or "Create coupon for partner"); otherwise a newsletter coupon you create later with the same name would credit that partner for every order. The coupon screen warns when the code of a coupon equals a partner code (also after saving). With WooCommerce active, "Create coupon for partner" on the partner's Codes tab creates a new coupon (code defaults to the selected partner code; percentage or fixed cart discount, amount, optional expiry, usage limit and individual use) and links it in one step; if the link cannot be saved, the coupon is deleted again. The action is recorded in the audit log.

**Automatic partner coupon** (since 0.15.0, Settings → Promotion → "Apply the partner's coupon automatically after a partner link", default off). When a visitor came through a partner link or short link and the partner has a linked WooCommerce coupon, the coupon is put into the cart once per shop session: when a product is added (also when the cart is created later in the same session) or when an existing cart is loaded – classic cart/checkout and the Cart/Checkout blocks. The coupon of the link's partner code is used, otherwise the partner's first linked coupon; only a coupon that attributes the order to the same partner (link active, coupon exists, code usable). WooCommerce checks the coupon as usual: an expired, used-up or not yet reachable coupon (minimum spend) is skipped silently and tried again after the cart changed. A coupon the customer entered is never removed: with an "individual use" coupon in the cart, or when the partner coupon is "individual use" and the cart already holds another coupon, nothing is applied; a coupon the customer removes is not applied again. Nothing is applied without a valid referral of this session (shop session or consented cookie, as for the attribution), for the partner's own purchases (own account or e-mail) or for paused, blocked or restricted partners. If the visitor later follows another partner's link (last touch), the coupon the plugin applied is replaced by that partner's coupon – also when no product is added afterwards (on the next page with the cart, since 0.16.0). Only one partner coupon per order (since 0.16.0, also with this setting off): when the customer enters a partner coupon, the coupon the plugin applied goes (with a short notice); a second partner coupon the customer enters while another partner coupon is in the cart is refused ("Only one partner coupon can be used per order"). The shop's own coupons can still be combined. Developers can allow several partner coupons with the filter `wpac_single_partner_coupon`. The customer sees one notice ("Your partner discount … was applied automatically"); in Store API requests no notice is added. The order stores `_wpac_auto_coupon` (coupon, partner) and the order box shows it; the attribution order (coupon priority setting) is unchanged, and coupon and link point to the same partner. The partner area shows "Your link gives customers 10% off …" next to the partner link; the welcome box shows the discount with `[wpac_partner_welcome discount="1"]` or the block option "Show the partner discount". Developers can refuse single cases with the filter `wpac_auto_apply_coupon` (bool, coupon code, partner ID).

**Code requests (own vanity codes).** Partners can request an easy-to-remember code such as MARIA10 in the partner area (tab "Links & codes", "Request your own code"). The request is checked like a code you create, and more strictly: letters A–Z, digits, "-" and "_" (starting and ending with a letter or digit), 3 to 20 characters (filter `wpac_code_request_max_length`), no reserved word (e.g. ADMIN, TEST, COUPON, the referral parameter and every name reserved for it, filter `wpac_reserved_partner_codes`; since 0.16.0 also typical names of shop campaigns such as WELCOME, NEWSLETTER, SALE, SOMMER, BLACKFRIDAY, XMAS or VIP, alone or followed by digits, "-" or "_", e.g. WELCOME10 or SALE-2027), not in the form of a generated code (4 + 4 characters such as ABCD-EFGH), and not already used as a partner code, as a linked coupon, as a WooCommerce coupon (a coupon with the same code would credit the partner) or as another partner's address (slug). A partner has at most one open request and can make 3 requests within 30 days (filter `wpac_code_requests_per_month`); the open request can be withdrawn. The requested code is reserved at once, so nobody else can take it meanwhile, but it does not work anywhere – not in links, at checkout or as a coupon – until you approve it. Open requests are listed at the top of the Partners page and on the partner's Codes tab; you receive an e-mail for each new request. **Approve** adds the code as an additional active code; the previous codes stay valid. Tick "Make main code" to make it the code shown to the partner – earlier codes stay valid, so printed links and coupons with them keep crediting the partner. With WooCommerce active you can also create a coupon with the new code (discount type and amount) or rename the coupon linked to the current main code to the new code. The rules are checked again on approval (e.g. a coupon with that name may have been created meanwhile). **Reject** needs a reason, which is sent to the partner; the code is free again. The partner is informed by e-mail in both cases; the three e-mails ("Partner requested an own code", "Requested code approved", "Requested code not approved") can be edited under E-mail templates. All decisions are in the audit log; requests are part of the privacy export and are deleted on erasure. Switch the feature off under Settings → Program → "Partners can request an own partner code".

**Partner area** (block "Partner area" or `[wpac_affiliate_portal]`): partner link with campaign builder (campaign, source and sub-ID), short link and QR code, codes, creatives (with embed code and sub-ID), statistics (period filter, conversion rate, earnings per month, report by campaign and sub-ID), commissions and payouts (filters, CSV export, without customer data), credit notes, payout details (bank and tax data), the partner's conditions and terms, e-mail preferences, account and privacy requests. The tab "Links & codes" starts with the labelling duty (the disclosure note from Settings → Promotion, e.g. "Advertisement", at the beginning of every post with a link, code, short link or QR code) and examples per channel. With Settings → Promotion → "Show the disclosure note visibly above the banner embed code" (default on) the HTML code for banners starts with the creative's disclosure note, so the label travels with the banner. The page with the partner area is never cached (`DONOTCACHEPAGE`), and partners land there after logging in (also from WooCommerce "My account", which gets a "Partner area" entry).

**Sub-IDs.** Partner links accept a sub-ID next to the referral parameter (`?partner=CODE&sub=placement-1`; parameter name via the filter `wpac_sub_id_param`). It is stored with the visit and the attribution (together with the visit ID) and shown to the partner per campaign and sub-ID (rows with fewer than 3 sales combined into "Other", see section 8).

**Broadcast mail.** Under Partners, "Write to all active partners" sends a plain-text e-mail to all active partners or one group, in batches of 50 in the background. Every mail has an unsubscribe link (type "broadcast"); partners can also switch announcements, commission notices and the monthly summary off under "My account".

## 3. Tracking, caching and CDNs

A sale is attributed to a partner by (in this order): a manual assignment by an administrator, a partner code entered at checkout, a partner coupon (if prioritised), a partner link (first or last touch), a coupon. Self-referrals (same account, same e-mail) are blocked or flagged for review.

**Partner links** look like `https://example.com/?partner=CODE` (parameter configurable) or `https://example.com/partner/slug/` (landing page). The visit is recorded without IP address (the referrer host only with marketing consent). The code is kept in an existing WooCommerce session (a cart) and – only with marketing consent – in the cookie `wpac_ref` (in a multisite network `wpac_ref_{site ID}`, filter `wpac_cookie_name`). A click alone never creates a shop session. Consent is read from the WP Consent API or the filter `wpac_has_marketing_consent`.

**Consent given after the landing.** Most visitors answer the consent banner after the page has loaded. On a landing page that was captured without consent, a small script (handle `wpac-beacon`) waits for the WP Consent API event `wp_listen_for_consent_change` and, when marketing consent is given, sends the referral again (`POST /wp-json/wpac/v1/touch` with `consent: true`), which sets the cookie without counting a second visit. Banners without WP Consent API support need **both** parts of a recipe in "Consent banners" below: the PHP filter `wpac_has_marketing_consent` (the server checks the consent again before it sets the cookie) and `window.wpacConsentGranted()` after consent (sends the referral of the landing page again). `wpacConsentGranted()` alone sets no cookie. If the visitor gives consent only on a later page, the referral is still kept when the first product is put into the cart from the landing page (the cart fallback reads the referring page and then also sets the cookie with consent).

### Consent banners

Integrations → System status shows "Consent banner connected" only when consent can really reach the plugin: a banner has registered a consent type with the WP Consent API (`wp_get_consent_type()` is not empty), or the filter `wpac_has_marketing_consent` is hooked. The WP Consent API plugin alone is not enough – without a registered banner it answers nothing, and the cookie is never set. Site Health ("Partner link tracking") and the setup checklist warn in that case. Partner codes and the shop session keep working without the cookie.

**Banners with WP Consent API support** – nothing else to do: install the "WP Consent API" plugin, switch on the banner's WP Consent API integration and put the cookie into the category **Marketing**.

- **Complianz:** supports the WP Consent API out of the box. Add the cookie under the category Marketing.
- **Real Cookie Banner:** supports the WP Consent API; create a service "Affiliate Captain" in the group Marketing with the cookie below.
- **Cookiebot (WordPress plugin "Cookiebot by Usercentrics"):** switch on the WP Consent API integration in the plugin settings and map Cookiebot's category "Marketing" to "marketing".

Check the result under Integrations → System status. If it stays on "No consent banner connected", the banner does not register with the WP Consent API on your site – use the marker recipe below.

**Banners without WP Consent API support** (e.g. Borlabs Cookie, Usercentrics, CCM19, Cookiebot without its plugin): use a small consent marker. The banner sets the first-party cookie `wpac_consent=1` when the visitor accepts the service "Affiliate Captain" and removes it on withdrawal; the plugin reads it on the server. Put the PHP part into a must-use plugin (e.g. `wp-content/mu-plugins/wpac-consent.php`):

```php
<?php
// Marketing consent for Affiliate Captain from the consent banner's marker cookie.
add_filter( 'wpac_has_marketing_consent', function ( $consent ) {
	return $consent || ( isset( $_COOKIE['wpac_consent'] ) && '1' === $_COOKIE['wpac_consent'] );
} );
```

Opt-in code (runs after consent; 34128000 seconds = 395 days – keep it equal to or shorter than the consent validity of your banner):

```html
<script>document.cookie='wpac_consent=1;path=/;max-age=34128000;SameSite=Lax';if(window.wpacConsentGranted){window.wpacConsentGranted();}</script>
```

Opt-out code (runs on withdrawal; the plugin then removes `wpac_ref` on the next page view):

```html
<script>document.cookie='wpac_consent=;path=/;max-age=0;SameSite=Lax';</script>
```

With a cookie domain (Settings → Tracking, e.g. `.example.com`) add `;domain=.example.com` to both codes. Where the codes go:

- **Borlabs Cookie 3:** Consent Management → Services → add a service "Affiliate Captain" in the service group Marketing; the opt-in and opt-out codes go into the fields of the same names, the cookie below into the service's cookie list. Instead of the marker cookie, PHP can also ask Borlabs directly: `function_exists( 'BorlabsCookieHelper' ) && BorlabsCookieHelper()->gaveConsent( 'affiliate-captain' )` (the service ID as set in Borlabs).
- **Usercentrics (Browser CMP):** create a data processing service "Affiliate Captain" (category Marketing) and, under Implementation → Data Layer & Events, a window event (e.g. `ucEvent`). Then load once on every page:

**Page caches.** Pages opened with the link parameter are sent with `DONOTCACHEPAGE` and no-cache headers, which WP Rocket, LiteSpeed Cache, W3 Total Cache, WP Super Cache and most hosting caches respect. Check that your cache does **not** ignore query strings for the link parameter (some caches strip unknown parameters such as `partner`). When the dashboard detects a caching plugin, a host cache or a proxy (Cloudflare, Varnish) while JavaScript tracking is off, it recommends the beacon mode below (filter `wpac_edge_cache` to name or hide the cache).

**Welcome box and caches.** Pages showing the partner welcome box (block or `[wpac_partner_welcome]`) are sent as not cacheable. The plugin finds the box in the content of the page, in active widgets (block, text and custom HTML widgets) and – in block themes – in the template and its template parts. Builders that store the layout elsewhere (e.g. Elementor data in post meta) are not checked: return `true` from the filter `wpac_needs_nocache` for those pages, or exclude them from the cache. The `/partner/slug/` redirect and the public code check `GET /wpac/v1/codes/{code}` are always sent as not cacheable. Prefetch/prerender requests (Speculation Rules, `Sec-Purpose: prefetch`) for partner links are declined (503) and `/partner/*` is excluded from WordPress' speculative loading, so only real clicks count.

**CDNs and edge caches** (Cloudflare APO, Varnish, Fastly) may serve the cached page anyway. Then enable Settings → Tracking → "Also record partner links via JavaScript": a small inline script with the handle **`wpac-beacon`** reports the link to `POST /wp-json/wpac/v1/touch`. Pages with partner links then stay cacheable for guests (no `DONOTCACHEPAGE`): the script records every guest visit, logged-in users are captured on the server. In optimisation plugins exclude `wpac-beacon` from "Delay JavaScript", "Combine/minify inline JavaScript" and lazy-loading of scripts, and make sure `/wp-json/wpac/v1/touch` is not cached or blocked by a firewall rule. The plugin adds the keyword `wpacBeacon` to the exclusion lists of WP Rocket (`rocket_delay_js_exclusions`), LiteSpeed Cache (`litespeed_optm_js_defer_exc`, `litespeed_optm_js_delay_exc`), Perfmatters (`perfmatters_delay_js_exclusions`) and FlyingPress (`flying_press_exclude_from_delay:js`, `flying_press_exclude_from_defer:js`), and gives the inline script `data-no-optimize="1"`, `data-no-defer="1"`, `data-cfasync="false"` (Cloudflare Rocket Loader) and `nowprocket`; other optimisers need the exclusion by hand. Plugins or firewall rules that block the REST API for guests ("Disable REST API", Perfmatters "Disable REST API for non-admins", Solid Security, WAF rules on `/wp-json/`) are handled in two ways: the route `wpac/v1/touch` is exempted in `rest_authentication_errors` (priority 999), and when the REST request is refused anyway the script sends the same data to `admin-ajax.php?action=wpac_touch` (same checks and answer). Site Health ("Partner links") and the monitor check the route with a request without cookies (at most hourly in Site Health, every 6 hours by the cron; result in the option `wpac_touch_probe`): "blocked" (REST and admin-ajax refused – every guest referral is lost) is critical, "REST blocked, admin-ajax works" is a recommendation. The script remembers the last reported referral of the tab in `sessionStorage` (`wpac_seen`: code, campaign, source, medium, sub-ID and path) once a request got through, so reloads and back navigation send no new request; a consent re-send always goes out. The touch request loads the WooCommerce cart only for guests that already have a shop session cookie (`wp_woocommerce_session_*`). A visit of the same browser (address + user agent) is counted once per minute; canonical redirects and reloads do not count twice. Visits of administrators and of the partner on their own link are not counted.

**Landing page and shop on different subdomains** (e.g. `www.example.com` and `shop.example.com`): enter the common domain `.example.com` under Settings → Tracking → "Cookie domain" (filter `wpac_cookie_domain`). The cookie, the cart fallback and the beacon (`Origin` check, filter `wpac_touch_allowed_origin`) then accept both hosts. A headless frontend on another domain can report links itself with `POST /wpac/v1/touch` once its origin is allowed with that filter.

**High traffic.** Settings → Tracking → "Record link visits (%)" writes only a sample of visits to the visit log (or none with 0, filter `wpac_record_visit`); attribution is not affected. Rate-limit counters are kept in a shared object cache (Redis/Memcached; not APCu, which is local to each server) or in a small table that is cleaned every hour.

**Checkout codes** typed in by customers work without any cookie or cache configuration – recommend them to partners who promote offline, in podcasts or on social media.

## 4. Commissions and rules

Commissions are calculated per order item on the net amount after discounts, without tax and shipping. Rules (Rules & groups) combine:

- **scope:** everyone, a partner group, one partner;
- **target:** all products, product IDs, categories, tags, SKUs/course codes (with `*`);
- **rate:** percent, fixed amount per unit (program currency), or exclusion.

**Which rule applies (Settings → Commissions → Rule precedence).**

- *Partner rules first* (default): an exclusion always wins; otherwise the scope counts first (partner > group > global), then the target (product/SKU > category/tag > all). Example: "Partner X / all products 3 %" beats "everyone / product 55 20 %", and a global exclusion of a category cannot be lifted for a VIP partner.
- *Most specific product first*: the target counts first, then the scope; exclusions compete like other rules (at the same rank the exclusion wins). Here "everyone / product 55 20 %" beats "Partner X / all 3 %", and "Partner X / category 7 15 %" lifts "everyone / category 7 excluded".
- Within the same rank the finer match wins: a rule for the variation before a rule for its parent product, an exact SKU before a wildcard (longer prefix first), the product's own category before a parent category (rules on a parent category apply to its subcategories). Then the priority, then the newest rule.
- `priority` only decides between rules of the same rank.
- The **lifetime rate** (if set) replaces all rates for repeat purchases of linked customers, including fixed amounts of product rules; only exclusions still apply.
- Fixed amounts count per unit (a bundle or composite product counts as one line; its parts are added to it) and never exceed the net amount of the line. Gift card purchases are not commissioned; discounts booked as negative fees and gift cards redeemed as payment lower the base.

The rate, base and rule are stored with every commission: changing a rule never changes past commissions. The rule preview shows which rule applies to a product.

**Lifecycle.** A commission starts as *pending* and is released (*approved*) after the hold period (Settings → Commissions; integrations can extend it, e.g. until a course has taken place). The hold period starts at payment, or – setting "Hold period starts" – when the WooCommerce order is completed (pre-orders, invoice, cash on delivery). Commissions of WooCommerce orders that are *on hold* (PayPal/Stripe disputes) or in a chargeback status are not released until the order is processing or completed again (filters `wpac_wc_hold_statuses`, `wpac_hold_release`). Refunds create negative correction lines, proportional per item; a cancellation, chargeback, trashed or deleted order reverses the rest; lowering order items after payment reduces the commission; raising them (higher quantity or price, an added line) books the difference as an extra line – an *Order increase* under the original commission at its rate (rule changes do not matter), a line added later at the current rules – for the same partner and with the hold period of the order (after a payout: in the next payout). Commissions that are under review, rejected or fully reversed are not raised; the order note then asks for a manual correction. A change back to a paid status (or restoring the order from the trash) reinstates a reversed commission; money that was refunded stays deducted. Each event is booked once only, even if it is reported several times. Corrections after a payout are deducted from the next payout. *Review* marks commissions held by a fraud rule. A rejected commission can be reopened for review (commission detail → Reopen); manual bookings (commission, bonus or deduction for a partner, or a correction of one commission) are approved at once and need a reason.

**Monthly tiers** add a bonus in percent of the monthly net revenue (or order count), either marginal (only above the threshold) or retroactive. **Lifetime commissions** give repeat purchases of a referred customer to the same partner. The binding is created only by an order with a customer account that earned a commission (never by a guest order, whose e-mail address is not verified), waits for the approval while the order is under review, and ends when the partner is terminated or lifetime commissions are switched off. The order box shows the binding of the order's customer and can remove it; `wp wpac customer-link` does the same from the command line. **Subscription renewals** (WooCommerce Subscriptions) are commissioned by default – not when the commission of the first order was rejected or fully reversed, under review when the first order is, and optionally only for a number of months (Settings → Commissions).

Every partner has an append-only, hash-chained account per currency (partner page → account statement). `wp wpac verify` and a daily check compare the accounts with the bookings.

## 5. Payouts: SEPA and manual transfers

1. **Payout details.** Partners enter name, address, country, tax status (business, small business, private), VAT ID or tax number and bank details in the partner area (administrators with `wpac_manage_payouts` can enter them on the partner page). IBANs are stored encrypted and shown masked.
2. **Payout run** (Payouts): choose the period end; the preview lists every partner with an approved balance and why someone cannot be paid (profile incomplete, no accepted terms, missing operator VAT ID for reverse charge, VAT ID invalid according to VIES, below the minimum, maintenance mode). Balances below the minimum and negative balances are carried forward.
3. **Credit note / statement.** Each payout gets a PDF with a gapless number per year (`GS-2026-000001`), stored in the statement folder and protected by a hash.
4. **Transfer.**
   - **SEPA (EUR):** select the payouts and download the SEPA XML file (pain.001.001.03) for your online banking. Needs the company account under Settings → Payouts & credit notes and the PHP extension `dom`.
   - **Manual transfer (any currency):** download the transfer list (CSV; separator ";", decimal comma and column names in the site language, readable in German Excel) and pay the amounts manually or by importing the list into your banking software.
   - **Other payment method (PayPal, Wise …):** partners can choose "other payment method" instead of an IBAN and enter free-text payment details (stored encrypted; switch it off under Settings → Payouts & credit notes – partners who already use it keep it until they change it). These payouts are left out of the SEPA file. The transfer list contains their payment details; **"Download PayPal payouts file"** creates the file for the mass payout upload in your PayPal business account (Pay & get paid → Payouts) for all selected payouts whose payment details contain an e-mail address – the others are listed and left as they are. There is no PayPal API connection: you upload the file and confirm the payout in PayPal yourself. Mention the payment provider as a recipient in your privacy policy (the suggested privacy text and the record of processing activities do so while the method is switched on).
   A payout can only be exported once; "export again" is only for files the bank did not process. After a download the page reloads and says what is in the file, what was left out and that the payouts are now "exported"; the status filter above the list shows e.g. all exported payouts that still have to be marked as paid.
5. **Mark as paid** after the bank (or PayPal) executed the transfer. Partners get an e-mail and see the date ("transferred on" for bank transfers, "paid on" for other methods).

The credit notes of a payout run are written in the background by the job queue (Integrations → queue), so runs with many partners do not time out; a payout can only be exported or marked as paid once its credit note exists (missing ones are written at that moment). There is no automatic payout rhythm: you start each run yourself (the former setting "payout period" had no effect and was removed).

**Read-only access for your tax advisor:** give the user the role "Tax advisor (Affiliate Captain, read only)" (or the capability `wpac_view_tax_data` alone). They see the payout list and the payout details and can download credit notes and cancellation documents, but cannot create, export or change payouts.

**Separation of duties:** approving commissions before the end of the hold period and assigning or re-assigning orders to partners need `wpac_manage_payouts`; partner managers (`wpac_manage_affiliates` only) cannot steer money to a partner and release it early. Linking, disconnecting or re-sending the account link, changing the e-mail address of a partner with partner area access or payout details, and the VIES check need `wpac_manage_payouts` too: whoever controls the partner's account or address could otherwise enter their own bank details.

**Password confirmation before money-relevant actions** (since 0.15.0, Settings → Fraud & abuse, on by default). Approving held bank details, linking a WordPress account to a partner manually, disconnecting it or sending the account link again, changing a partner's payout details on the partner page, downloading the SEPA file, the transfer list or the PayPal payouts file and marking payouts as paid ask for your WordPress password first – since 0.16.0 also the actions that create money or redirect it: a manual booking ("Book a manual commission or deduction"), "Approve commissions" (single and bulk; rejecting or reopening is not asked), "Create payouts", creating a payout from a payout request, writing off a negative balance, booking a repayment and changing a partner's e-mail address. The confirmation is valid for 15 minutes in the current login session (filter `wpac_reauth_ttl`); another browser, a new login or a logout needs a new one. With the [Two-Factor](https://wordpress.org/plugins/two-factor/) plugin active for your account, its second factor (e.g. the authenticator code) is asked as well; other 2FA plugins can connect through the filter `wpac_reauth_verify`. Your form is kept on the server meanwhile (encrypted, for 5 minutes, only for your login session) and carried out right after the confirmation – for a download the file starts on the confirmation page; go back to the Payouts page afterwards. More than 5 wrong attempts within 15 minutes block the confirmation for that time; successful confirmations do not count (since 0.16.0). Every confirmation and every refused attempt is in the audit log ("Password confirmed for a money-relevant action", "Password confirmation failed"). Switching the setting off needs a confirmation too. WP-CLI commands and the REST API are not affected (they use their own authentication, e.g. application passwords); the filter `wpac_reauth_required` exempts or adds actions.

**Changing bank details in the partner area** (IBAN, payment details or payout method) needs the partner's current password; the partner and the previous address are informed by e-mail. Exports refuse payouts whose partner changed the details after the payout was created. Within 30 days after the partner's e-mail address changed or a user account was linked, new bank details entered in the partner area wait for approval on the partner page ("Approve bank details", `wpac_manage_payouts`); until then payouts go to the previous account, and the partner (also at the previous address) and the admin are informed. Disconnecting an account informs the partner and the admin as well.

**Terminating a partner** with "open commissions are rejected" cancels the partner's payouts that were not exported yet (cancellation document) before the commissions are rejected; already exported payouts are listed for you to check. Write-offs and repayments are never rejected.

**Objections** of partners against a credit note appear on the Payouts page. For unpaid payouts, cancel and create a corrected one; a paid payout cannot be cancelled – issue a correction credit note instead, or explain why the credit note is correct.

**Correction credit notes** (paid payouts, with or without an objection: objection notice or payout details → "Issue correction credit note"; needs `wpac_manage_payouts` and `wpac_view_tax_data`). Enter the correct net amount and a reason. The plugin issues a document with its own gapless number series (`KG-2026-000001`, prefix in Settings → Payouts) that names the corrected credit note and shows the amounts before (the credit note, or its latest correction), the corrected amounts and the difference – net, VAT and gross with the VAT treatment frozen on the credit note. The gross difference is booked to the partner account (booking type *correction*): a shortfall is paid with the next payout run, an overpayment is offset against later commissions (negative balance carried forward). The next credit note lists it under "Correction credit notes settled" without adding VAT again. A form can be submitted once only (one-time key, and it is refused when the credit note was corrected in the meantime); a further correction starts from the previous one. The booking cannot be rejected. Issuing is audited, an open objection is marked as handled with the correction's number, and the partner receives the PDF by e-mail and finds it in the partner area next to the credit note. Correction credit notes appear in the annual overview and are deleted after the retention period counted from their own date.

*What a correction changes.* The amounts are the **taxable net** of the credit note per VAT treatment and rate, taken from its lines – each line keeps the treatment valid when the service was rendered (e.g. a partner who was a small business then and is VAT-registered now). Repayments, write-offs and settled correction credit notes on the credit note are not taxable and are never part of a correction; a credit note that consists only of them cannot be corrected (correct the credit note the amounts came from). The VAT is always computed on the corrected net (never "VAT before + VAT of the difference"), so a chain of corrections that ends at 0 leaves exactly 0. A credit note with **several parts** (different VAT treatments or rates) is corrected part by part: the form shows one input per part, and every part you change gets its own correction credit note that names the part it corrects. The §19 small business warning counts a correction with its net difference on its own date (not again with the later credit note that settles it); the next credit note shows settled correction credit notes on a line of their own, outside the net amount and the VAT.

*Refunds after a correction.* Correction credit notes are not linked to individual commissions. A refund or cancellation of an order that is booked **after** a correction credit note of the same payout is deducted from the partner account automatically as usual – if the correction already took this order into account, the partner is charged twice. The correction form therefore lists the orders of the credit note (do not include later refunds of these orders in a correction), and when such a refund arrives the plugin writes an audit entry (`payout.refund_after_correction`), adds an order note (WooCommerce) and shows a warning with the payout's correction credit notes. Check the case and, if necessary, issue a further correction credit note; the booking itself is not changed automatically.

*Manual bookings and refunds (since 0.15.0).* A manual booking for one commission (a deduction such as a contractual penalty, or a bonus) stays as it is when the order is refunded later: the refund only reduces the calculated commission (the sale and its increases) in proportion, and a full refund reverses exactly that. Before 0.15.0 such bookings were counted as if they were earlier refunds (a penalty of 20 € reduced the later reversal by 20 €, a bonus was reversed with the order).

*Increases and full reversals.* When an order is cancelled or refunded in full, commission increases of that order that are still pending (not released yet) are rejected together with the reversal, so the reversal only takes back what was approved or paid. Partial refunds work as before.

*Amounts in forms* (manual bookings, repayments, correction credit notes, settings) are read per currency: "1.000,50", "1,000.50" and "1 000,50" are the same amount, "1.000.000" is one million; a lone group of three digits such as "1.000" or "12,345" is refused as ambiguous (write 1000 or 1.000,00) – except in currencies without decimals (JPY) or with three or more (KWD, BTC), where it is read as shown in the form; input with more decimals than the currency has (e.g. "12,3456" or "0,125" in euros) is refused instead of rounded.

**Cancelling** a payout (before or after export, with a reason) releases its commissions for the next run and, for credit notes, creates a cancellation document (`ST-…`). **Payout requests:** if enabled, partners request the payout of their approved balance; you create the payout from the request or reject it with a reason.

**Negative balances** of ended partners (clawbacks without new earnings) can be written off with a reason or claimed back with up to three payment requests; repayments are booked on the partner page. The claim includes the VAT that was paid out with the original credit note (a refund corrects it, §17 UStG): 100 € commission paid with 19 % VAT and refunded later means a claim of 119 €. Repayments and write-offs are not taxable themselves. Once the balance is settled (fully repaid or written off), a correction document (`GS-…`, "Correction of credit notes") is issued automatically and sent to the partner; it reduces the net amount and VAT of the original credit notes, nothing is transferred.

A payout is never created with a negative or too small **gross** amount: VAT corrections of earlier credit notes count (e.g. after a change of the tax status), the balance is then carried forward.

## 6. Credit notes and VAT

With **self-billing** (Settings → Payouts & credit notes, on by default) the plugin issues credit notes in the name of the partner (Gutschrift, §14 Abs. 2 UStG). This needs a prior agreement – put it into your partner terms; payouts are blocked for partners who have not accepted terms.

| Partner | VAT on the credit note |
|---|---|
| business in your country | your VAT rate is added (payout = gross) |
| business in another EU country | reverse charge, no VAT; partner VAT ID required and checked with VIES |
| small business (e.g. §19 UStG) | no VAT, note on the credit note |
| private person | no VAT |

Commission rates are net amounts. Legal references on the documents follow your country (German, Austrian or Swiss law for DE, AT, CH; the EU VAT Directive for other countries, whose credit notes are titled "Credit note (self-billing)"). For reverse charge your own VAT ID is required. Outside DACH or if self-billing is not agreed, switch self-billing off – the plugin then creates payout statements and partners send you invoices. The treatment can be adjusted with the filter `wpac_vat_treatment`.

**VAT by the time of the service.** The VAT treatment of each commission follows the tax data and the VAT rate valid when the commission was earned (for corrections: of the original commission), not the day of the payout. Every change of a partner's tax status, country or VAT ID and every change of the VAT rate keeps the previous values with the time until which they applied. A credit note can therefore show lines with different treatments (e.g. December as small business without VAT, January with 19 %); each treatment gets its own note. Corrections of earlier credit notes keep the treatment of the original credit note.

**Tax data of partners.** Partners enter tax status, VAT ID or tax number in the partner area. A VAT-registered business may give a tax number instead of a VAT ID (§14 Abs. 4 UStG); reverse charge across borders needs the VAT ID. VAT IDs are checked for their format and – for partners in an EU country – for the country prefix. Changes that change the VAT on credit notes (a first declaration as VAT-registered business, a new tax status, a new VAT ID of a business) only take effect after you approve them on the partner page (Payout details → Approve tax data); until then the previous data apply, and the approved data only apply to commissions earned from then on. Every change is logged with the old values and reported to you by e-mail. Under Payouts, small business partners whose credit notes alone exceed the small business limit (25,000 € previous year / 100,000 € current year, filter `wpac_small_business_limits`) are listed.

**Language.** Credit notes are always written in the site language (with WPML/Polylang the default language; frozen with the document, whoever creates it). For languages the PDF fonts cannot show (Cyrillic, Greek, Arabic, Asian scripts) English is used (filter `wpac_statement_locale`). Names and addresses with characters outside Western European (Ł, ś, ř, ő …) are transliterated (Ł → L); the original spelling is kept in the document properties and listed in a note on the document. A Unicode font is not embedded (it would make every PDF several hundred KB larger).

**Sending.** Every credit note, correction document and cancellation is e-mailed to the partner with the PDF attached when it is issued (a credit note takes effect once the partner received it; filter `wpac_notify_credit_note`). A cancellation document that could not be written is retried hourly.

**Electronic invoice (e-invoice, EN 16931).** Every credit note, correction credit note (Korrekturgutschrift) and cancellation (Storno) can also be downloaded as an electronic invoice: a UN/CEFACT CII XML file according to EN 16931, next to the PDF (partner area → Payouts: link "(XML)"; admin: Payouts → statement → "E-invoice (XML)" and the correction credit note list). Downloads use the same permission and nonce checks as the PDF; the file is named like the PDF (`GS-2026-000001.xml`).

- *Why:* in Germany, credit notes between domestic businesses are invoices (§14 Abs. 2 UStG). From 1 January 2027 (partners with more than €800,000 turnover in the previous year) and from 1 January 2028 (all VAT-registered partners) such a credit note must be an e-invoice in a structured format; a PDF alone is no longer a proper invoice and endangers the input VAT deduction. Small businesses (§19 UStG) are exempt. Until the end of 2026 a PDF credit note needs the partner's consent to the format – put it into your partner terms.
- *Content:* built from the same frozen data as the PDF (partner data snapshot, operator data, items, VAT treatment), so both show the same amounts. Self-billing: the partner is the seller, you are the buyer. Document type 389 (self-billed invoice) for credit notes, 384 (corrected invoice, with a reference to the corrected credit note) for correction credit notes and correction documents of a payout run, 381 (credit note, with a reference to the cancelled credit note; same amounts as the credit note, the type reverses them) for cancellations. VAT categories per line: S (VAT rate, one breakdown per rate), AE (reverse charge, with exemption reason), E (small business: "Kein Ausweis von Umsatzsteuer, da Kleinunternehmer gemäß § 19 UStG") and O (private individual). Repayments, write-offs and settled correction credit notes are no service: they appear as "paid amount", so the amount due is the payout amount of the PDF. A credit note that consists only of such amounts is a payment notice and has no e-invoice.
- *Profile:* XRechnung 3.0 (`urn:cen.eu:en16931:2017#compliant#urn:xeinkauf.de:kosit:xrechnung_3.0`) when all data XRechnung demands on top of EN 16931 are known – among them a phone number of the seller, which the plugin does not collect from partners. Otherwise the file declares the EN 16931 core profile (`urn:cen.eu:en16931:2017`); that is just as much a valid e-invoice under §14 Abs. 1 UStG (XRechnung is mainly required by public buyers). Add-ons can add the phone number or the partner's IBAN (filter `wpac_einvoice_data`; with an IBAN the payment means is SEPA credit transfer 58, otherwise "mutually defined" with the masked account as text – only the masked IBAN is stored with a credit note). The buyer reference is the optional setting "Buyer reference on e-invoices (e.g. Leitweg-ID)", otherwise the document number.
- *Which file counts:* the XML is the e-invoice; the PDF is a visual copy with the same content. The PDF does **not** contain the XML (no ZUGFeRD/Factur-X): that would need PDF/A-3, which the built-in PDF writer cannot produce. Archive the XML together with the PDF; it is built again from the stored data on every download while the PDF exists and is no longer available after the retention period.
- *By e-mail:* Settings → Payouts & credit notes → "Send e-invoice (XML) with the credit note e-mail": **Automatic** (default: attached for partners whose credit note shows German VAT, i.e. domestic VAT-registered businesses of a German operator), **Always** or **Never** (download only).
- *Checks:* every XML is checked against the main business rules of EN 16931 (totals BR-CO-10/13/14/15/16/17, VAT breakdown BR-S-08/BR-AE-08/BR-E-08, exemption reasons, VAT identifiers, decimals, payment means) and, for the XRechnung profile, the BR-DE rules for mandatory data; problems are written to the plugin log. The plugin's CI additionally checks sample files of every document kind and VAT category (both profiles) with the official KoSIT validator and the XRechnung configuration (`tests/einvoice`). This does not replace a check of your own data: validate a real file with the KoSIT validator before going live, and have the VAT treatment confirmed by your tax advisor.

**VIES (opt-in).** The check is **off by default** (it is an external request); switch it on in Settings → Payouts & credit notes → "VIES check". When on, EU VAT IDs of partners are checked with the VIES service of the European Commission (in the background after saving, daily for older results of active partners; your VAT ID is sent along for a qualified confirmation with consultation number). An invalid result (also for a domestic VAT ID, and for a malformed number) blocks credit notes with VAT or reverse charge; "unavailable" blocks nothing and is retried. If VIES refuses your own VAT ID, the check runs without it and the partner page says so. When the check is switched off again, earlier results no longer block; timeout and daily limit can be changed with the filters `wpac_vies_timeout` and `wpac_vies_daily_cap`. Without the check you are responsible for verifying partner VAT IDs yourself (e.g. on the VIES website) before reverse-charge payouts.

**Retention.** Credit notes, payout data and the accepted terms are kept for the statutory period (at least 10 years for the PDFs; DE 8, AT 7, CH 10 years for booking records, counted from the end of the year) and deleted afterwards. "Tax audit / legal hold" stops all deletion. Objections of partners against a credit note are listed under Payouts.

## 7. Fraud and abuse

Settings → Fraud & abuse: maximum orders per partner in 24 hours, maximum order value, minimum seconds between click and order, maximum refund rate, disposable or blocked e-mail domains. Hits put the commission into *review* with the reason; approve or reject it in Commissions. Self-referrals are blocked (or flagged). Partner code checks, the application form and the touch endpoint are rate limited per client. Behind Cloudflare or a reverse proxy, enter its IP ranges under "trusted proxies", otherwise all visitors share one rate limit (Site Health → "Partner links" warns when a request arrives through an unconfigured proxy). The client address is then read from `X-Forwarded-For`; `CF-Connecting-IP`/`X-Real-IP` only when enabled with the filter `wpac_client_ip_headers` (only safe if every trusted proxy sets these headers). Every limit can be changed with the filter `wpac_rate_limit` (`$limit, $bucket, $window`, buckets e.g. `code_check`, `rest_code`, `register`, `visit`). The beacon itself is never limited – a referral is not lost behind a CDN.

## 8. Privacy

- No IP address is stored for attribution; visits keep the referrer host, campaign and landing content only, and are deleted after the retention period.
- The affiliate cookie is only set with marketing consent (cookie mode "consent", default). The suggested privacy policy text names the legal basis that matches the setting: with "consent" the consent (Art. 6(1)(a) GDPR, § 25(1) TDDDG); with "Always, without consent" it claims no legal basis for the cookie but leaves a placeholder and a note for you in the policy guide: without consent the cookie is only allowed if it is strictly necessary (§ 25(2) no. 2 TDDDG), which affiliate cookies usually are not – in the EU they usually require consent. Site Health ("Partner links") shows the same recommendation while "always" is set. With "Keep the code from a partner link in the WooCommerce shop session" the partner code is stored with an existing shop session on the server in every cookie mode (no cookie of its own; the session cookie of the cart is used); the text describes this with legitimate interest (Art. 6(1)(f) GDPR) as for the attribution without cookie. The texts are a suggestion, not legal advice: have them reviewed by your data protection advisor.
- Partners never see customer names or contact details. They do see, for their own orders, the order number, date, product name, amounts and status – check whether product names in your shop allow conclusions about customers (e.g. health products). Campaign and sub-ID are not shown per order, only in the statistics by campaign and sub-ID; there every row with at least one but fewer than 3 sales in the period is combined into one row "Other" (k-anonymity: with a unique sub-ID per reader, a row with one sale would tell the partner who bought). Rows with link visits only and the row without campaign and sub-ID stay on their own. Filter `wpac_subid_min_group` (default 3, 1 = off). Admin reports show every row. The grouping applies per selected period; comparing overlapping periods can still narrow a sale down, so keep sub-IDs coarse when you brief partners.
- Customers can object to the attribution of their orders and to the lifetime link (Art. 21 GDPR); the suggested privacy policy text says so. Remove the link in the "Affiliate Captain" box of the order or with `wp wpac customer unlink`.
- Cookie lifetime: the settings accept up to 3650 days but warn above 395 days (13 months), which data protection authorities usually consider the limit for consent-based cookies. The lifetime is named in the privacy policy text and belongs into the cookie list of your banner (see "Consent banners" in section 3).
- Proof of accepted terms: the version hash covers the **rendered** text of the terms page (blocks including synced patterns, shortcodes, tags removed), and that text is stored once per hash (option `wpac_terms_text_{hash}`, together with the block source). A change of a synced pattern on the terms page therefore also yields a new hash and stored text; acceptances from before keep counting as long as the version number is unchanged – increase it for material changes.
- The terms template (dashboard → "Create pages automatically") contains clauses on independence (no commercial agent, no indemnity under § 89b HGB), the format of credit notes (PDF, e-invoice where required, consent to the PDF format during the transition period), changes of the small business status, the labelling duty with examples and the data protection roles. It is a starting point – have it checked by a lawyer before publishing.
- Lifetime links store a keyed hash (HMAC-SHA256) of the customer, not the e-mail address. The key is generated once and stored in the option `wpac_customer_key` – in the same database, so the hashes are pseudonymous: with a database dump, e-mail addresses could be guessed by trying candidates. Define `WPAC_CUSTOMER_KEY` (at least 32 characters) in `wp-config.php` to keep the key out of the database. It is only used while **no customer links exist** (new installations, or after all links have expired or were removed): e-mail addresses are not stored, so existing hashes cannot be recalculated with a new key. If links already exist, the stored key stays in use and Site Health, `wp wpac health` and Integrations → System status report the constant as ignored. Once the constant is in use, the generated key is deleted from the database and only a fingerprint of the constant is kept (`wpac_customer_key_constant`, an HMAC with the WordPress auth salt, so a database dump alone does not allow guessing the constant – generate it at random, e.g. `openssl rand -hex 32`); do not change or remove the constant afterwards – returning customers are then no longer recognised and erasure requests no longer find their links. The fingerprint of the earlier key is then kept and Site Health, `wp wpac health` and Integrations → System status keep warning (state `wpac_customer_key_changed`) until the earlier key is back, the links made with it have expired, or an admin confirms the change under Integrations → System status – either deleting the links made with the earlier key (they can no longer be matched to anybody) or, if only the WordPress salts changed and the key is the same, without deleting.
- Bank details are encrypted; tax and bank data are only visible with `wpac_view_tax_data`.
- WordPress privacy tools: personal data export and erasure for partners and customers. Records that must be retained are restricted (Art. 18 GDPR) instead of deleted and erased when the retention period ends.
- The export (Art. 15 GDPR) shows the person's IBAN and the details of another payment method (e.g. the PayPal address) **masked** (last 4 digits), with a note where the complete details are available (partner area → payout details; on request from you). Decision (0.13.1, reverses the "full IBAN" of 0.13.0): the export file lies unencrypted in `uploads/wp-personal-data-exports/` (public URL with a random name, link by e-mail, in backups and offload plugins), so the full IBAN there would bypass the encryption at rest and the separate "view tax data" permission. It also lists the change log entries about the partner (a positive list of actions and detail fields: no fraud flags, no IDs of other partners with the same IBAN, no order or customer references), earlier tax data, the reasons of commission status changes (refund reasons, internal fraud notes and other free texts only as a neutral label – like the partner area, refunds, write-offs and manual bookings show their type, not the shop's free text, which can name the customer, Art. 15(4) GDPR) and the e-mails the partner unsubscribed from.
- Erasure for a partner empties the details of their change log entries, except acceptance records and the booking-relevant entries the audit clean-up keeps for the statements (payout details – tax data changes, VAT ID checks – payout requests, payouts, statements, commissions, balances, tiers): these stay while they are within the statutory retention period, pseudonymised (tax IDs masked to e.g. `DE•••789`, names, addresses, free texts and error texts removed), and the eraser response reports them as retained with the reason (with "keep forever" or a legal hold it says that they are not deleted automatically). Entries that are no booking records (refused or failed changes of the payout details, other partners with the same IBAN, rejection reasons of payout requests) are emptied at once. The history of the partner's tax data (`wpac_tax_history_{id}`) is deleted together with the payout details: it only decides the VAT of new payouts of earlier services, while correction credit notes use the payout's own items and snapshot. While payout details are retained because something is still open, the history stays with them.
- Erasure for a customer removes the lifetime links and the referral data on their orders (order meta `_wpac_touch`: code, campaign, sub ID, visit ID; `_wpac_partner_code`: the code the customer typed in; `_wpac_manual_affiliate`: an admin's assignment) – not needed once the order is attributed or can no longer be (paid without a partner, cancelled). They are kept, and reported as retained, while the order's booking waits for an automatic retry or the order is not paid yet (it is attributed on payment). Attributions of their orders stay as booking records of the partner commission and are reported as retained with the reason.
- Attributions (order number, partner, method, campaign, sub ID, visit ID) are deleted daily once they and every commission of the order are past the statutory retention period and nothing of the order is open (not during a legal hold). Afterwards the commission rows of the order are pseudonymised: the order number becomes a keyed hash (one per order, so order counts stay right), product and description are emptied, the idempotency key is hashed (a re-delivered sale of the order is still recognised as a duplicate) and the reasons of their status changes are deleted; partner, amounts, status and dates stay for the partner account and reports. Undecided and rejected applications are anonymised in batches until none is left (within the daily time budget, the rest in the next run), except applicants whose processing is restricted (Art. 18 GDPR); their VIES result, previous e-mail address, requested changes, account-link token and mail opt-out go with them. Applications that were confirmed but never decided are anonymised after Settings → Data & maintenance → "Keep undecided applications" (default 365 days); unconfirmed applications (e-mail not confirmed) expire after 2 days.
- WooCommerce orders belong to the shop: the order notes written when an order is attributed (they name the partner) and the order meta `_wpac_*` stay with the orders when a partner is erased or the plugin is deleted. Remove such notes in WooCommerce yourself if a partner's erasure requires it.
- Logs: e-mail addresses in logged exception messages and mailer errors are masked (`a***@***.de`).
- Settings → Privacy → Policy Guide contains a suggested text based on your settings (including the VIES recipient); Settings → Data & maintenance offers a record of processing activities (German template for German admin languages, otherwise English; filter `wpac_ropa_language`).
- Erasure of a partner with many link visits: the visits are deleted in batches of 5000 rows (filter `wpac_visit_erase_batch`), each its own short transaction, for at most 10 seconds per eraser request (filter `wpac_erase_request_budget`). When visits are left, the eraser answers `done: false` and WordPress calls it again with the next page until they are gone; the partner is listed in the option `wpac_visit_erasure_pending` and a single event (`wpac_erase_visits`, 20 seconds per run, filter `wpac_visit_erase_budget`; the daily run as backup) deletes the rest also when the browser tab is closed. The same applies to the anonymisation of ended partners and applicants by the retention. Afterwards the partner's rows of the daily visit aggregate (`wpac_visits_daily`, visits per day, campaign and sub-ID) are deleted the same way.
- External services: only the VIES check (European Commission) and a loopback request to your own site, see readme.txt → External services.

## 9. Multisite

- **Network activation** sets up every site in batches (large networks finish in the background); new sites are set up automatically.
- Every site has its own tables, settings, partners, payouts and credit note numbers. Partners of one site are not partners of another.
- Deleting a site drops its tables – except the booking records (partners, commissions, payouts, accounts, audit log, terms acceptances) while a credit note is within the statutory retention period: they stay in the database, the site's credit notes are moved to `wp-content/uploads/wpac-retained/site-<id>/` (with `WPAC_STATEMENT_DIR` they stay in its `site-<id>` folder), and the daily maintenance deletes both once the period has ended. Deactivating or deleting the plugin works per site.
- WP-CLI commands work on one site (`--url=…`); `--network` runs `status`, `health`, `upgrade`, `jobs`, `cron` and `verify` on every site where the plugin is active.
- A deleted WordPress user is disconnected from the partner automatically (also when removed from a site); the partner page offers "Disconnect WordPress user" as well.
- With `WPAC_STATEMENT_DIR` all sites use the folder you define; use a folder per network that only holds credit notes, back it up, and never clean it manually.
- Capabilities are granted to the administrators of each site; super admins have them everywhere.

## 12. Monitoring

- **Site Health** (Tools → Site Health) shows the checks: schema, scheduled tasks, failed sales/refunds, account consistency, unwritten credit notes, publicly reachable statement folder, own encryption key, maintenance mode.
- **Alarm mail:** a daily check e-mails the notification address when a critical check fails.
- **HTTP endpoint** for uptime monitors: set a monitoring token (at least 20 characters) under Settings → Data & maintenance, then call

  ```
  curl -fsS -H 'X-WPAC-Monitor-Token: <token>' https://example.com/wp-json/wpac/v1/health
  ```

  `200` = OK, `503` = a critical check failed (the body names the failing checks, no details).
- **Logs:** errors go to the WooCommerce logger (WooCommerce → Status → Logs, source `affiliate-captain`; entries written before 0.11 are under `wp-affiliate-captain`) or, without WooCommerce, to the PHP error log (lines start with `Affiliate Captain error:` / `warning:`). Logged are: failed jobs (the first failure and the final one, with exception class, file and line), sales/refunds that could neither be booked nor queued (hook `wpac_contract_not_queued`), e-mails that could not be sent (with the reason of the mailer), credit notes that could not be written (with the cause), aborted migrations and failed scheduled steps. With `WP_DEBUG` (or the filter `wpac_log_debug`) also repeated job failures and skipped mails. Every administrative change is in the audit log.

### E-mails (sender, Reply-To, partner e-mails)

All e-mails of the plugin go through one function (developers: filter `wpac_mail`, actions `wpac_mail_sent` / `wpac_mail_failed`, see [CONTRACT.md](CONTRACT.md)). Settings → Program → E-mails:

- **Sender name / address:** empty = WordPress default (or your SMTP plugin). Use an address of your own domain (SPF/DKIM), otherwise mails may land in spam.
- **Reply-To:** mails to partners and applicants carry the notification e-mail as Reply-To, so "please reply" (payment request, bank details changed …) reaches you and not `wordpress@…`.
- **Partner e-mails:** payout paid (on by default; the text names the bank account only for SEPA payouts), new/approved/rejected commissions (off by default; at most one mail per partner and run). The monthly summary, the commission mails and broadcast mails contain an unsubscribe link and the headers `List-Unsubscribe` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click` (RFC 8058). Opening the link only shows a confirmation page with a button (mail scanners that open links in advance do not unsubscribe anybody); the button, or the one-click of the mail program, stores the choice.
- **E-mail templates** (Affiliate Captain → E-mail templates, capability "Manage program"): subject and text of every partner mail with placeholders such as `{name}`, `{link}`, `{code}`, `{rate}`, `{portal_url}`, `{amount}` (the editor lists the placeholders of each mail). Unchanged templates use the built-in, translated text; a changed template is sent as written (e.g. informal "du" instead of "Sie"), "Reset to the built-in text" discards it, "Send test e-mail to me" sends the saved template with example values to your own address. The layout "Simple HTML" sends these mails as HTML (values escaped, web addresses as links) with the plain text as alternative part. The welcome mails contain the partner link, the code and the commission rate. The filter `wpac_mail` still runs after the template.
- **Applicants** get a confirmation after the double opt-in ("we received your application"); the operator mail about a new application is written in the operator's language (user language of the account with the notification address, otherwise the site language) and has the applicant as Reply-To.
- A failed mail is logged with the reason (see Logs above).

### Add-ons: API, branding and events (contract 1.3.0)

Add-ons never read the plugin tables. Since contract 1.3.0 they use public PHP functions to read partners and commissions (`wpac_get_affiliate(s)`, `wpac_get_commission(s)`) and to change them with the same rules, e-mails and audit entries as the admin (`wpac_update_affiliate`, `wpac_set_affiliate_status`, `wpac_set_commission_status`, `wpac_create_adjustment`). These functions do not check permissions themselves – an add-on that offers them over REST must require the capability "Manage partners" (or "Manage payouts" for early approvals). Every change appears in the audit log under the logged-in user. The partner area shows no plugin name; a white-label add-on can add its logo, header and footer, CSS classes and its own tab labels, and set the e-mail sender name. Every new ledger booking (including correction credit notes, write-offs and repayments) and every cancelled payout triggers an event after it is saved, e.g. for webhooks. Since 0.15.0 a manual booking of an add-on can name the commission it refers to (e.g. a team commission for a recruited partner's sale) and a short reference; the link is shown in the booking's history ("Refers to commission #…") for information only – refunds of that commission, payouts and credit notes treat the booking like any other manual booking. Add-ons with their own e-mails use the partner area link in the partner's language and the sender name and address from the e-mail settings, and can react when a creative is saved, approved or archived. Details: [CONTRACT.md](CONTRACT.md), "Lese- und Schreib-API (1.3.0)".

## 13. Troubleshooting

| Symptom | Cause and solution |
|---|---|
| Commissions stay "pending" forever | Scheduled tasks do not run. Set up a system cron (section 1); `wp wpac cron hourly` releases due commissions immediately. |
| A sale has no commission | Check the order box "Affiliate Captain" on the order: attribution, the reason for "not attributed" (no referral, unknown/expired code, partner not active, self-referral, renewals), review flags and a running retry; refused sales also leave an order note. Failed bookings are in Integrations → Retry queue (retry there or `wp wpac jobs --retry-failed`; failed sales are kept until they are retried or dismissed). Codes of paused/terminated partners or expired codes are not accepted. |
| Partner links are not counted | Full-page cache or CDN serves the page: see section 3 (JavaScript tracking, exclude `wpac-beacon`, do not strip the link parameter). |
| Application form says "nonce" or "expired" | The page was served from a cache for more than a day: exclude the application page from the cache. |
| A partner cannot be paid | The payout preview and the notice on the plugin pages name the reason (profile incomplete, tax data waiting for your approval, current terms not accepted, your VAT ID missing, VIES invalid, below minimum including VAT corrections). |
| A downloaded credit note is marked "DUPLICATE" | The original file is missing on this server (several app servers without shared storage, lost file) and could not be rebuilt identically. Put the statement folder on shared storage (section 1) and restore the original from the backup. |
| SEPA export fails with "dom" | The PHP extension `dom` is missing: ask your host, or use the transfer list (CSV). |
| "Bank details cannot be decrypted" | The encryption key changed (WordPress salts changed or `WPAC_ENCRYPTION_KEY` set/changed later). Restore the old key; otherwise partners must enter their IBAN again. |
| "Credit notes are publicly reachable" | The statement folder in uploads can be downloaded (typical on nginx). Define `WPAC_STATEMENT_DIR` outside the web root or deny access to `/wp-content/uploads/wpac-statements/`. |
| "Database update incomplete" | Run `wp wpac upgrade` and check the database user's ALTER privileges; scheduled tasks pause until the schema is complete. |
| "Some tables do not use InnoDB" | Convert them: `ALTER TABLE wp_wpac_commissions ENGINE=InnoDB;` (for each listed table). |
| "Partner accounts differ from their bookings" | Run `wp wpac verify`; do not edit plugin tables by hand. Contact support with the output before the next payout. |
| VIES shows "unavailable" | The VIES service of the member state is down; the check is repeated daily. Nothing is blocked. |
| Import: "code already in use" | Partner codes are unique across the program; choose another code or leave the column empty. |
| Partners or the operator get no e-mails | Look for "E-mail could not be sent" in the log (reason of the mailer). Set a sender address of your own domain (Settings → Program → E-mails) or use an SMTP plugin; check whether a partner unsubscribed (monthly summary/commission mails only). |
| A sale is missing although the order is paid, nothing in the retry queue | Search the log for "could not be processed and could not be queued" (database was unavailable): send the order again (change the order status or `wp wpac jobs`). |
| A job stays "queued" with error `no_handler` | The integration of that job type is not active (e.g. WooCommerce deactivated). The job is retried hourly without using up attempts; reactivate the integration. |
| A job keeps failing | `wp wpac jobs list --status=failed` shows the last error; the log has the first failure with file and line. Fix the cause, then "Retry" in Integrations → Retry queue or `wp wpac jobs --retry-failed`. |
| Scheduled tasks look stuck | `wp wpac status` shows the last hourly/daily run; see "Server cron" in section 1. |

Before contacting support, collect: `wp wpac support` (anonymized), `wp wpac health`, the Site Health info (Tools → Site Health → Info → "Affiliate Captain", contains the same anonymized data) and the relevant log and audit log entries.

## 14. Uninstalling

Deactivating keeps everything. Deleting the plugin removes settings, partners and visits only if "Delete all data when the plugin is deleted" is on – and even then keeps commission, payout and credit note records that are still within the statutory retention period. The partners table is kept with them, pseudonymised ("Deleted partner", no contact data), because the records refer to its partner numbers. If you install the plugin again, these numbers stay reserved, so a new partner never gets a former partner's number, credit notes or balance; "Delete all data" is then off. The pages created by the setup assistant (application, partner area, landing page) are moved to the trash when they still contain the plugin's block. To delete the kept records once the period has ended, upload the plugin again (do not activate it) and run `wp eval-file wp-content/plugins/affiliate-captain/tools/purge-retained.php` (folder `wp-affiliate-captain` for versions up to 0.10). On a network the tool checks every site (no `--url` needed) and also deletes the kept tables and credit notes of deleted sites once their period has ended. On large networks delete the plugin with `wp plugin uninstall affiliate-captain` (no time limit): in a request whose time limit cannot be lifted, the uninstall stops after 80 % of `max_execution_time` (filter `wpac_uninstall_time_budget`, seconds, 0 = no limit) and records the sites it did not reach in the network option `wpac_uninstall_incomplete`. Export the program (section 10) before you delete the plugin. WooCommerce orders are never changed by the uninstall apart from one case: their order notes and the order meta `_wpac_*` (partner code entered, referral snapshot) stay with the orders, which belong to the shop; only the manual partner assignment by partner number (`_wpac_manual_affiliate`, `_wpac_manual_own`) is removed when the partners table is deleted, because a new installation gives these numbers to new partners. For the same reason the link of coupons to partner code rows (`_wpac_code_id`) is always removed.

## 15. Downgrade and rollback

Every update with a database change (see "Upgrade Notice" in the readme) raises the schema version. An older plugin version leaves a newer schema untouched and shows a notice "The database belongs to a newer version" – it does not migrate back, and code that does not know the new tables or columns may write incomplete records. A rollback therefore means:

1. Before the update: a database backup (all `{prefix}wpac_*` tables and the `wpac_*` options) and a copy of the statement folder (`WPAC_STATEMENT_DIR` or `uploads/wpac-statements`).
2. Rollback: switch on maintenance mode, install the old plugin version, restore the database backup **and** the statement folder from the same point in time. Bookings, payouts and credit notes made since the update are lost with it – book them again or stay on the new version and report the problem.
3. Only installing the old version (without restoring the backup) is a stopgap: it keeps working on the newer schema, but tables it does not know are left behind. Example: 0.12 added `{prefix}wpac_payout_corrections` (correction credit notes, PDFs in the statement folder). Deleting 0.11 afterwards with "Delete all data" does not remove that table and those PDFs; delete them by hand once their retention period has ended, or install the newer version again and uninstall that one.
4. Index-only schema changes (e.g. 0.13: indexes on the audit log and the order number of commissions) are harmless for an older version: it ignores them.

**Large tables (update to 0.14).** Schema 14 widens the visit index `affiliate_created` to `(affiliate_id, created_at, campaign, sub_id)`, so the partner statistics by campaign and sub-ID are answered from the index alone (measured: a partner with a million visits in 30 days 54 s → 11 s; a second, wider index would not be chosen while the narrow one exists). The key is replaced online in one statement (`DROP KEY …, ADD KEY …, ALGORITHM=INPLACE, LOCK=NONE`), with the same lock timeout, warning and 5-minute retry as the indexes of schema 13; `verify_schema()` (Site Health, `wp wpac upgrade`) also reports a key that still has the columns of an older schema. In addition the statistics of the partner area (overview and statistics tab: summary and campaigns) and the "Partner traffic" box in the editor are cached for 10 minutes per partner (or page) and period in transients `wpac_pstats_*`; new visits show with the next 10-minute bucket, bookings at once (they raise the report generation `wpac_reports_gen`, at most once per request, not autoloaded). Schema 15 adds the daily aggregation of the visits (see below). The rate-limit table is cleaned up hourly in batches of 5000 rows for 20 seconds (filters `wpac_rate_limit_purge_batch`, `wpac_rate_limit_purge_budget`); while expired rows are left a single event (`wpac_purge_rate_limits`) continues every 3 minutes, and the monitor warns when it has not caught up for six hours (then use a shared persistent object cache such as Redis for the counters).

**Daily visit aggregation (update to 0.14, schema 15).** The table `wpac_visits_daily` holds the number of link visits per partner, local day (site time zone), campaign and sub-ID (unique key on these four, index on the day; no personal data, not a booking record). Each visit written to the visit log adds 1 in the same request (one `INSERT … ON DUPLICATE KEY UPDATE`), so the aggregate follows the sampling setting "Record link visits (%)" exactly like the raw visit log: with 10 % both count the sampled tenth (no extrapolation), with 0 neither counts anything. Visits recorded before the update are added by a background job (`wpac_visits_daily`, started by the migration and by the hourly maintenance): it reads the visits in ID order in steps of 20,000 (filter `wpac_visits_daily_batch`), for 20 seconds per run (filter `wpac_visits_daily_budget`), moves its cursor in the same transaction as the counts (resumable after a timeout or crash, nothing counted twice) and continues one minute later until done; partners whose visits are being erased are skipped. The limit between the backfill and the live counting is stored in the options table together with `MAX(id)` in one statement, and the live upsert checks it in its own statement, so a visit is counted either by the job or live, never by both. Until the backfill is complete, and after a change of the site time zone (the aggregate is then rebuilt, because its days are local days), all reports count the raw visits as before. Once complete, the visit counts of the partner area (overview, statistics: summary and campaigns), the admin reports by partner and by campaign, the monthly report mails and the REST report are read from the aggregate; the report by content (landing page) and the editor box still count raw visits (the aggregate has no content column). The visit retention ("Delete link visits after … days") applies to the aggregate as well, by whole local days before the cutoff (the boundary day is kept until it is completely past the period); erasing a partner deletes their aggregate rows after their visits. The campaign table in the partner area shows 25 rows per page, each page cached separately (a partner with thousands of sub-IDs no longer produces a transient beyond the 1 MB of Memcached). Filter `wpac_visits_daily_ready` (false) makes the reports always read the raw visits. Uninstalling drops the table (also when booking records are kept).

**Recruiter column (update to 0.15, schema 16).** Schema 16 adds the column `referred_by` (partner ID of the recruiter, 0 = none, with an index) to `wpac_affiliates` by `dbDelta`; existing partners get 0. The partner table is small, so no online index step is needed. See "Recruited by" in chapter 2.

**Large tables (update to 0.13).** Schema 13 adds two indexes (audit log: action and date; commissions: order number). They are added online (`ALGORITHM=INPLACE, LOCK=NONE`; about 2 s per million audit rows on MariaDB 10.11), and a schema change waits at most 10 seconds for a table lock (filter `wpac_migration_lock_wait_timeout`) instead of queueing every following write behind it. If an index cannot be added without blocking writes (MyISAM tables, very old servers, a long open transaction), it is skipped: bookings continue, Site Health shows a warning, and the index is retried every 5 minutes by the cron and by `wp wpac upgrade`. With more than about a million audit rows, or on Galera/Percona XtraDB Cluster (where any ALTER blocks writes in the whole cluster), run the update in a quiet period and migrate with `wp wpac upgrade` instead of an admin page view.
